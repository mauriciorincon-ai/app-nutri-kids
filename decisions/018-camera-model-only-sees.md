# ADR-018 — The camera: code first, the model only sees

**Status:** accepted · **Date:** 2026-11-20 · **Sprint:** S012 · **Owner decisions:** G-Plan S12 «1a 2a»: S12 is what the camera sees (photo → recipe, look at the plate) and S13 is labels and the supermarket; the model sees and the code cooks. The phone test at the close of F1 is the DECISION look (≤ 200 MB, ≤ 20 s per photo, ≥ 7 of 10 with at most one invented). The rest are builder defaults, listed below.

## Context

The owner asked for photo → recipe. Hard rules 5 and 6 apply in full: no paid or third-party API in the runtime, and the child's data (a photo of the kitchen or the plate counts) never leaves the phone in the clear. The order rule 5 sets is: the system model the phone already has → a local embedded model → the feature does not exist and code answers. Browsers do not yet ship a vision model to web pages, so this is the second step: a small open model that runs inside the page.

## Decision

1. **The model only sees.** It returns TEXT (a list of names). Which of those names is a food the app knows, its traffic light, the recipe and every warning are decided by code over the loaded plan and the recipe catalog (`src/lib/camera/match.ts`, pure). No id is ever born from the model's text: what does not match by name goes to «it saw this, but it isn't in your catalog», is shown, and goes nowhere. Nothing enters the pantry or the day without a tap from the carer.
2. **Model:** `HuggingFaceTB/SmolVLM-256M-Instruct` (Apache-2.0), pinned by Hub commit `d039ab0d…` in `src/lib/camera/model.json`. Weights: embeddings int8 (28.4 MB) + vision encoder q4 (63.8 MB) + decoder q4 (86.6 MB) = 178.8 MB. Measured on the Mac: the q4f16 vision encoder returns an empty answer on WebGPU (it emits end-of-utterance at once), so the q4 files are used for both engines. Changing the model is an owner decision.
3. **Runtime:** `@huggingface/transformers` 4.3.2 (exact; published 2026-10-27; Apache-2.0), the only new dependency. `scripts/build-sw.mjs` copies `transformers.min.js` (which bundles onnxruntime-web) and its `ort-wasm-simd-threaded.asyncify.{mjs,wasm}` into `public/ia/` (gitignored, like `public/pdfjs/`) and stamps `public/ia/vision-worker.js` from `scripts/vision-worker.template.js`. By default the runtime would fetch its `.wasm` from a CDN; `wasmPaths` points it at `/ia/`.
4. **No route imports the model.** The screen creates `new Worker("/ia/vision-worker.js", { type: "module" })` with a literal URL that the bundler does not follow, and only after the tap. The CI gate `scripts/check-model-isolation.mjs` (job `quality`, after the build) fails if any chunk in `.next/static` or `.next/server` carries runtime markers; it was shown failing with `scripts/demo-rojo.sh`.
5. **The only network is the model download after the tap.** Inside the worker, `guardedFetch` is the runtime's `fetch`: GET only, no body, only to the app's origin or `huggingface.co` over https (the Hub then redirects to its own CDN). Anything else is rejected with `blocked-request`. Unit tests run the stamped worker in a sandbox; the screen's e2e (with a simulated worker; the real model never runs in CI) must show zero requests before the tap and zero during the analysis.
6. **The photo never leaves the phone and is never saved.** It enters through the system file picker (`<input type="file" accept="image/*" capture="environment">`), so the page never asks for camera permission and rule 24 does not apply. `createImageBitmap` scales it to 512 px, the bitmap is closed, the pixels are TRANSFERRED to the worker (the page keeps no copy), the input is cleared, and the worker drops its reference after generating. Errors leave the worker as a code, never with content.
7. **Engine:** WebGPU when `navigator.gpu.requestAdapter()` answers, otherwise WASM with one thread and no proxy (no COOP/COEP: they would break the rest of the app). The same files serve both engines, downloaded once.
8. **Caching:** the runtime keeps the weights and the `.wasm` in the `nutrikids-model` cache; the service worker keeps `/ia/*.js|mjs` cache-first in `nutrikids-ia-<hash of runtime version + stamped worker>`. Fixed along the way: the service worker used to delete EVERY cache that was not its own on `activate`, which would have erased the downloaded model with each new version; now it only deletes old `nutrikids-(shell|pdfjs|ia)-*` caches. A contract test covers it (rule 19).
9. **From text to names (code).** Only the first sentence counts (after it the model describes the scene). It is split on commas, «and», «with», «including», «like», «or» and place prepositions; preambles («the image shows», «the food items include»), colours, cooking adjectives and numbers are stripped; fragments that name the scene (table, background, market…) or carry digits are dropped; at most 12 names. The English «-oes» plural is folded so «potatoes» matches «potato».
10. **The test panel** («How the engine is doing») shows the engine, transferred MB, load time, per-photo time and the four criteria; each name has ✓/✗ and «Copy results» copies plain text (engine, sizes, times, counts, short OS and browser). It never includes the photo.

## Consequences

- The camera is useful only where the phone can run the model: without Worker or WebAssembly the screen says so and offers ticking by hand in Recipes.
- The first use costs a ≈ 180 MB download; the screen says the size before the tap and recommends wifi.
- A small model invents: that is why nothing enters without a tap, the result always says «double-check it with an adult», and the decision to ship rests on the owner's phone test.
- Measured on the Mac (Chrome, 10 photos under CC0 or public domain from Wikimedia Commons, kept only in the scratchpad): WebGPU 189 MB transferred, 7.1 s to load, 0.6 s per photo; WASM 9.8 s per photo (max 10.0 s).
